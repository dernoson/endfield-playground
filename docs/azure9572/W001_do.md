# W001 材料組合無法處理 實作紀錄

## 1. 任務概要
實作 CR-09 中的 `W001_unmatchedMaterial` 偵測器。此偵測器負責在設備輸入材料不符任何配方時，發出黃色警告（Warning）。此功能為純函式，僅依賴 `ValidationContext` 進行靜態分析。

## 2. 參考的檔案
- **規格與需求**：
  - `docs/azure9572/MILESTONE_0726.md`：確認任務範圍與權責分配。
  - `spec/09_recipe_warning.md`：W001 警告觸發條件（材料組合無法處理）。
- **介面與型別定義**：
  - `src/types/validation.ts`：`Detector`, `Alert`, `ValidationContext` 的型別定義。
  - `src/types/machine.ts` 與 `src/types/flow.ts`：`Machine` 和 `RecipeDef` 的資料結構。
- **參考實作**：
  - `src/composables/useFlowEngine.ts`：參考其 `validateRecipeMatch` 以及處理分流器（Splitter）時的邏輯。

## 3. 使用的資料結構
- **`ValidationContext`**：
  - `devices (FactoryNode[])`：走訪所有設備。
  - `connections (FactoryEdge[])`：查詢各設備的上游與下游關係。
- **`Set<string>`**：
  - `visited`：用來記錄遞迴走訪圖形時已經造訪過的節點 ID，避免循環依賴導致無限迴圈。
  - `incomingItemIds`：收集所有上游管線帶來的品項 ID，使用 Set 可以快速去重並提供 `has()` 方法以 O(1) 速度驗證配方輸入。

## 4. 程式碼邏輯與演算法

### 4.1 遞迴尋找上游材料 (`getIncomingItems`)
由於 W001 執行於流量計算前（沒有 `outputRates`），我們需要自己推斷管線裡裝了什麼。
- **基本邏輯**：找到指向當前設備的所有 `inEdges`，讀取其 `sourceNode`。
- **分流器穿透**：如果 `sourceNode` 是一般的製造機，我們直接讀取它當前配方（`recipeIndex`）的 `outputs`。但如果 `sourceNode` 是「分流器」或「管道分流器」，因為它沒有配方，我們必須呼叫自己（遞迴）繼續往更上游找，直到找到有配方的源頭設備為止。

### 4.2 設備配方比對 (Main Run Loop)
1. **過濾不需要檢查的設備**：如果設備本身沒有輸入口（如產線起點 `is_source`），或者設備沒有任何可用配方，則直接略過。
2. **過濾空管線設備**：如果設備沒有接上任何入邊（`inEdges.length === 0`），則略過（此情況交由 E004 處理，避免產生重複且無意義的 W001 警告）。
3. **收集輸入**：利用前述的 `getIncomingItems` 取得 `incomingItemIds`。
4. **驗證所有配方**：利用 `getRecipesForMachine(machineType)` 取得該設備的所有可用配方。只要**有任何一個配方**的 `inputs` 完全被包含在 `incomingItemIds` 裡面（即上游有供給該配方所需的所有材料），就不會觸發警告。
5. **拋出警告**：如果走訪完所有配方都不滿足條件，則推入一個 `W001` 的 `Alert`。

## 5. 做的假設 (Assumptions)
- **與 E004 的邊界釐清**：假設「當一個設備要求輸入，但完全沒有接上任何管線」時，是屬於 `E004 (輸入缺失)` 的範疇。為了避免畫面上同時出現 E004 和 W001，在 W001 判斷中，遇到無任何連入管線時會主動跳過。
- **當前配方的預設值**：在向上游追溯產出時，如果上游設備尚未指派 `recipeIndex`，會假設它使用 `recipeIndex = 0`（第一筆配方）來推算產出，避免因 `undefined` 導致崩潰。
- **分流器行為**：假設分流器的唯一作用是轉發上游物品，因此將它視為透明節點，在偵測時直接追溯到其更上游的產出來做為判定依據。
