## 主題簡述

CR-07 多目標優化產能推導 —— 獨立頁面，讓使用者在不考慮設備擺放位置的前提下設定產能目標與原料限制，由系統以線性規劃推導最佳配方流量分配，再透過「切換視角以導入」部署到佈局視角。

規格出處 `spec/07_optimization.md`（v0.3），整份屬 Phase 3，spec 自述「實作細節可依 Phase 2 完成後的使用回饋進一步調整」。

**本計畫的約束**

- `spec/` 是對外文件，統籌決斷寫在本計畫，不寫回 `spec/`。
- `待實作` 代表「規格已定、尚未逐項對照程式碼確認」；本 CR 在 `src/` 中沒有對應實作（見 O1）。
- 開工前先確認 Phase 2 的使用回饋是否已推翻本 CR 的既有設計；若有，先改規格再動工。
- 設備台數是流量分配的衍生結果（向上取整），**不是決策變數**。任何把台數當輸入的實作都違反本 CR 的核心模型。

## 規劃描述

依 spec 主要章節切格：核心概念（流量單位與決策空間）、三類輸入設定（原料上限、硬性需求、優化目標）、LP 求解、無解處理、結果呈現、微調聯動、部署，最後以驗證表格收斂。

三類輸入拆成三格而非一格，因為硬性需求是選填、次要目標權重也是選填，兩者可以獨立延後；擠成一格會讓「原料設定做完了但硬性需求還沒」這種常見中間狀態無處可記。

求解與無解處理分開：無解是使用者一定會遇到的路徑（原料不足以滿足硬性需求），有獨立的驗證項與獨立的 UI 呈現，不是求解的邊緣情況。

### O2 · 2026-08-11 03:30:00+08:00 — 流量單位在 CR-07 有第二套定義

### O3 · 2026-08-11 05:05:00+08:00 — 確認未動工，且求解套件尚未進依賴；但 30/min 這個常數已在程式碼裡

複查：`src/app/` 下只有 `App.vue`、`layouts/MainLayout.vue` 與 `dev/` 六個 debug 頁，`router/index.ts` 沒有優化頁面路由；`src/` 內沒有任何 LP / solver / glpk 相關檔案；`package.json` 的 dependencies 也沒有求解套件。0003#6 的選型仍是動工前提。

但 O2 說的「1 條 = 30 個/min」已經以 `BELT_RATE_LIMIT = 30`（`types/flow.ts:13`）活在 FlowEngine 裡，並實際用於限流（另有 `PIPE_RATE_LIMIT = 60`）。所以本 CR 的顯示換算不必另定常數，該引用同一個來源；同時也代表 0003#4 若改動基準單位，動到的不只是本 CR 的模型，還有 FlowEngine 既有的兩個常數與其測試。

### 1 流量單位與決策空間定義

- **state:** 待實作
- **needs:** 0003#4
- **basis:** → O2

以傳送帶滿載流量（30 個/min）為 1 條 —— 該常數已存在於 `types/flow.ts` 的 `BELT_RATE_LIMIT`，顯示換算引用同一份，不另定（O3）。決策變數是分配給每個配方的流量（連續值，個/min）；設備台數是衍生計算 `⌈分配流量 / 單台設備產出速率⌉`，不是決策變數。目標函式為最大化調度券產出（或依使用者設定的多目標權重）；約束為原料供給上限與部分產物的硬性最低需求。

### 5 LP 模型建立與求解

- **state:** 待實作
- **needs:** 0003#6、0010#1
- **basis:** → O3

以連續線性規劃求解，純前端執行、無後端。模型：最大化 `Σ(recipe_i 的調度券產出率 × x_i)`；約束為每種原料 j 的 `Σ(recipe_i 消耗原料 j 的速率 × x_i) ≤ 供給上限 j`、每種硬性需求產物 k 的 `Σ(recipe_i 生產產物 k 的速率 × x_i) ≥ 下限 k`、以及 `x_i ≥ 0`。求解結果是每個配方的最佳分配流量。

求解套件未選型且尚未進依賴（0003#6、O3），授權與 bundle size 若不可接受則整條實作路徑要重來。應考慮 lazy load，只在優化頁面載入求解器。

判準：spec 第 4 節「多配方競爭原料」通過（求解優先分配調度券產出高的配方）。

**沿革**

- H1 · 2026-08-11 決斷 —— 自 `spec/07_optimization.md` 3.2 節轉入（來源：spec）
