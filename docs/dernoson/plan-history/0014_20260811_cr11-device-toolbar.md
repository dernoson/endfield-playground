## 主題簡述

CR-11 產線擺設編輯區 - 工具列 —— 畫面下方列出所有可用設備，以與終末地相同的分類方式用 Tab 切換；點選設備觸發物件資訊面板顯示，並可在任意視角把設備拖曳到畫布上放置。

規格出處 `spec/11_toolbar.md`（v0.1，Phase 1）。這份是最晚從 CR-01 拆出來的一份，成熟度明顯低於其餘十份（見 O1），本計畫的重點之一是把未定的部分標成待決斷而不是替它補規格。

**本計畫的約束**

- `spec/` 是對外文件，統籌決斷寫在本計畫，不寫回 `spec/`。
- `待實作` 代表「規格已定、尚未逐項對照程式碼確認」；`ToolbarPanel.vue` 已存在（見 O2），動任一格前先核對現況。
- 拿起設備之後的所有互動屬 CR-01 的狀態機，本 CR 只負責「拿起」這個入口，不複製一套流程。

## 規劃描述

依 spec 主要章節切格：從工具列拿起、拖曳擺放、分類 Tab、搜尋過濾、中繼器隱藏，最後以驗證表格收斂。

「拖曳擺放」是唯一一個 `待決斷` 而非 `待實作` 的格子：spec 只寫「使用者在任意視角都能直接拖動出來設備到畫面上放置（互動細節待補）」，沒有定義它與單擊拿起的關係，也沒有定義「任意視角」在流程視角下是什麼意思。這是規格缺口，需要使用者補，不由 agent 推測。

### O1 · 2026-08-11 03:20:00+08:00 — CR-11 是從 CR-01 拆出且規格尚未補齊

`spec/11_toolbar.md` 版本 v0.1，全檔 67 行，是 12 份 spec 中最短的一份。文件自述：「本文件內容自 `01_canvas_and_devices.md` 拆分而出（原 2.3「從工具列拿起」、5.3「下方設備工具列」、5.4 工具列快捷鍵列、部分驗證項目），細節待依 `00_top_spec.md` CR-11 的敘述持續補齊。」2.2 節「拖曳擺放」正文只有一句話並標「互動細節待補」。

### O2 · 2026-08-11 03:25:00+08:00 — 工具列側既有實作盤點

`src/editor/toolbar/ToolbarPanel.vue` 對應下方設備工具列；`src/app/dev/MachineCatalogPanel.vue` 與 `ProductCatalogPanel.vue` 是 L1 的設備 / 產物目錄 debug 頁；`src/data/machines.ts` 與 `src/types/machine.ts` 持有設備定義與分類。

`MachineCatalogPanel.vue` 在 `dev/` 下，代表設備清單的資料側已經可以列舉並瀏覽 —— 工具列要做的是把同一份資料換成正式 UI 並加上分類 Tab、搜尋與拿起互動，不是從零建資料層。

### O3 · 2026-08-11 04:55:00+08:00 — 工具列是五個寫死按鈕，與設備庫無關；dev 頁反而已有分頁與搜尋

`ToolbarPanel.vue` 全檔 84 行：一個寫死的五項陣列（精煉爐 / 粉碎機 / 組裝台 / 輸送帶節點 / 電力節點，型別是 `EquipmentType` 而非 `Machine`），單擊呼叫 `editorStore.armPlacement`，`dragstart` 把代號寫進 `dataTransfer`（`FactoryCanvas.handleCanvasDrop` 接得住，落點即放置）。沒有分類 Tab、沒有搜尋框、沒有讀 `machineList`、沒有圖示 —— 是純文字按鈕。其中「組裝台」「輸送帶節點」「電力節點」三個名字在 `machineList` 裡不存在（詳見 0004 的觀察）。

反而 dev 頁 `MachineCatalogPanel.vue` 已經有 0014#3 / 0014#4 要的東西：依 `machine.tags` 的分頁（含「未分類」頁）、跨欄位搜尋（名稱 / id / tag）、每台的 W×H 格點埠示意與 JSON。

`Machine` 介面沒有 `allowInBase` 欄位（O1 的斷鏈引用因此仍無出處）。中繼器實際有兩台（中繼器、息壤中繼器），都在「電力」tag 下。

所以 CR-11 的形狀是：0014#3 / #4 不是從零做，而是把 dev 頁的分頁與搜尋搬成正式 UI 並換掉五個寫死按鈕；0014#5 要先加欄位（或改用其他判定規則），且案例是兩台不是一台。

### O4 · 2026-08-17 09:55:00+08:00 — 工具列本身沒動，但它放出來的東西現在連接口都沒有

- **更新:** O3

`dev/paper`、`dev/toby`、`dev/cake` 合入後（`8838faf` → `c8c1cb3`，`src/` 只動六個檔案），`ToolbarPanel.vue` 一行未改，仍是五個寫死的 `EquipmentType` 按鈕。變的是下游：`FlowNodeOverlay` 的埠 Handle 改為依 `getMachine(data.machineType)` 動態產生，查不到機型就一顆都不畫（詳見 0004 的 O7）。

`EquipmentType` 的五個英文代號 `getMachine()` 全部查不到，所以從工具列放到畫布上的設備現在**沒有任何接口可以拉線**。這條路以前的問題是「放出來的節點 FlowEngine 認不得」，現在是「使用者根本連不上它」。

對 CR-11 的意義：0014#1 的入口（單擊 → `armPlacement`）依舊可跑，但它交付的東西已經不可用；把五個寫死按鈕換成真的設備庫（0014#3、0014#4，前提是 0004#13）從「規格對齊」升級為「讓工具列產出可用節點」。

## 待辦

### 1 從工具列拿起設備

- **state:** 實作中
- **needs:** 0004#3、0004#4
- **basis:** → O3、O4

左鍵單擊工具列中的設備 → 物件資訊面板更新顯示該設備資訊（CR-01 的情境 A）→ 滑鼠進入「拿起設備」狀態，游標跟隨設備半透明預覽。

單擊已呼叫 `armPlacement`，`placementArmed` 也確實會讓下一次點畫布放置設備。但三件事都沒有：面板不會更新（0004#3 未做）、沒有跟隨游標的預覽（0004#4）、放置後不會續拿（0004#7）。所以入口有了，入口之後的行為還不存在。

而且入口交付的東西現在是壞的：放出來的設備因為機型代號查不到 `machineList`，一顆接口 Handle 都不會渲染（O4）。本格即使把上游三項補齊，只要 0004#13 沒收，使用者放完設備仍然什麼都接不上。

拿起後的互動（Edge Scrolling、`R` 鍵旋轉、`Esc` 取消、放下、連續放置）全部沿用 CR-01 的狀態機（0004#4），本格只負責入口。

判準：spec 第 4 節「工具列單擊拿起設備」「工具列拿起連續放置」兩項通過，且放置後的設備拉得出管線。

### 2 拖曳擺放的互動定義

- **state:** 待決斷
- **basis:** → O1、O3

spec 只寫「使用者在任意視角都能直接拖動出來設備到畫面上放置」，並自標「互動細節待補」。

補充一項現況：程式碼裡**已經有一版**拖曳擺放 —— `ToolbarPanel` 的 `dragstart` 把設備代號寫進 `dataTransfer`，`FactoryCanvas.handleCanvasDrop` 在放開處直接放置（等同單擊放置，無朝向選擇、無 `Esc` 處理、拖到畫布外即無事發生）。這是既成事實而不是規格決定；使用者裁決時可以把它當作「現有行為」來取捨，但不應視為已定案。

需要使用者補的是：拖曳與 2.1 節的單擊拿起是兩套並行的入口，還是單擊拿起的另一種觸發？拖曳放開時等同「單擊放置」還是進入朝向選擇模式？「任意視角」包不包含流程視角 —— 若包含，拖到 Flow Chart 上要發生什麼？拖曳中途按 `Esc` 或拖出畫布外的行為為何？

在補齊之前不實作，以免做出一套之後要整個換掉的互動。

### 5 以 allowInBase 隱藏中繼器

- **state:** 待實作
- **needs:** 0004#13
- **basis:** → O3

`allowInBase: false` 的設備不允許擺放，自動從工具列隱藏；任何情況下電力分類 Tab 中都不應出現中繼器。

`Machine` 介面確認沒有 `allowInBase` 欄位（O3），所以本格的第一步是補欄位：決定加在 `Machine` 介面與來源 JSON，或改用其他判定規則（例如以 id 白名單）。另外中繼器實際有兩台（中繼器、息壤中繼器），規則要涵蓋兩台而非一台。
