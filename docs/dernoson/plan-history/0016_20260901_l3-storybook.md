## 主題簡述

為 `src/components/` 底下的 L3 純展示元件建立 Storybook，讓每個元件能獨立掛載、窮舉 props 組合，不必把整條 app 跑起來才看得到某一種狀態。

現在做得起來，是因為 L3「不得 import store」這條硬規則已在全樹成立（唯一命中是 `BaseRegionSelector/Index.vue:51` 的型別引用，執行期會被抹除）。每個 L3 元件都能單獨掛載，story 不需要 Pinia decorator。

工具已定：Storybook ＋ `@storybook/vue3-vite`（見 O1）。

**本計畫的約束**

- 不為了讓 story 好寫而改 L3 元件的行為。story 寫不出來代表 props 介面有問題，回報給使用者，不改元件遷就 story。
- story 檔與元件同資料夾（`Index.stories.ts`），與 CLAUDE.md 第 2 節的元件資料夾慣例一致。
- `.storybook/` 要納入 ESLint 與 Prettier 的涵蓋範圍。

## 規劃描述

先裝套件與骨架，把 preview 的執行期前置（Tailwind、Nuxt UI plugin、Vue Flow CSS）補齊，再依外部依賴的難度分三批寫 story：無外部依賴的 6 個、走 Nuxt UI 的 1 個、需要 Vue Flow context 的 8 個。第一批同時是 preview 設定是否正確的驗證。

掛載位置（`/dev/storybook/<component>`）與 CI 涵蓋兩件事尚未定案，各自獨立成格。

## 觀察與推論

### O1 · 2026-09-01 03:05:00+08:00 — 候選套件只有 Storybook 相容於本專案的 Vite 8

`npm view` 實測：`@storybook/vue3-vite@10.5.10` 的 `peerDependencies.vite` 是 `^5 || ^6 || ^7 || ^8`，涵蓋專案的 Vite 8.0.10；`storybook@10.5.10` 的 peer 只有 `prettier`、`vite-plus`、`@types/react` 三項且全部 optional，不會拖進 React 依賴。`@storybook/addon-vitest@10.5.10` 的 peer 是 `vitest: ^3 || ^4`，與專案的 4.1.6 相容，但另外要求 `@vitest/browser` 與 `@vitest/browser-playwright`。

唯一的 Vue 原生對手 Histoire 停在 `1.0.0-beta.1`，`peerDependencies.vite` 是 `^7.3.0`，**不含 Vite 8**，且最後發布為 2026-01-07。要採用就得靠 `overrides` 硬壓 peer 範圍，把風險轉嫁到一個停滯的 beta 上。Ladle 只支援 React。

所以工具選擇沒有實質分歧：相容於現有 Vite 8 / Tailwind 4 / Vitest 4 的只有 Storybook 一條路。

### O2 · 2026-09-01 03:08:00+08:00 — L3 的 15 個元件依外部依賴分成三批

`src/components/` 下 15 個 `.vue`：8 個 import `@vue-flow/core`（`FlowChart/` 的 6 個節點與邊元件、`FlowChart/Index.vue`、`DeviceNode`），1 個用 Nuxt UI（`ShortcutRow/Index.vue` 的 `UButton` / `UKbd`），其餘 6 個只依賴 Vue 或無外部依賴。

沒有任何元件在執行期存取 Pinia。`BaseRegionSelector/Index.vue:51` 的 `import type { BaseRegion } from '@/store/canvasStore'` 是型別層對 store 層的反向依賴，不影響掛載，但值得記著。

Vue Flow 那 8 個靠 inject 取得畫布上下文，單獨掛載會失敗，需要把元件包進 `<VueFlow>` 的 decorator 並餵最小的 `nodes` / `edges`。這批的成本明顯高於其餘 7 個，所以要排在最後。

### O3 · 2026-09-01 03:12:00+08:00 — preview 要重現 main.ts 的四項執行期前置

`src/main.ts` 在掛載 app 前做了四件事：import `./style.css`、註冊 `@nuxt/ui/vue-plugin`、import `@vue-flow/core/dist/style.css` 與 `theme-default.css`。少任何一項，對應那批元件在 Storybook 裡就沒有樣式或直接掛不起來。

`vite.config.ts` 另有 `@nuxt/ui/vite` 的 `ui()` plugin 與 `@` alias。Storybook 的 vite builder 會讀專案的 `vite.config.ts` 並合併，理論上兩者都會生效——**但這一點尚未實測**，Nuxt UI 的 app config 與 color mode 在 Storybook 環境下是否完整仍是未知。

### O4 · 2026-09-01 03:30:00+08:00 — 元件計數更正：7 / 7 / 1，不是 8 / 6 / 1

- **更正:** O2

`src/components/` 底下 15 個 `.vue` 的實際分布是：`FlowChart/` 7 個（`Index`、`DeviceNode`、`MaterialNode`、`ProductNode`、`WarehouseNode`、`PendingImportNode`、`FlowEdge`）依賴 `@vue-flow/core`；`ShortcutRow/Index.vue` 1 個用 Nuxt UI；其餘 **7** 個（`BaseRegionSelector/Index`、`MachineShape`、`StatsPanel/` 的 5 個）只依賴 Vue 或無外部依賴。

O2 寫的「8 個 Vue Flow、其餘 6 個」是數錯，兩邊各差一。有機器後果：第 6 格的判準原本寫「8 個元件都能掛載」，會多要求一個不存在的元件。

### O5 · 2026-09-01 03:35:00+08:00 — Vite 設定確實被合併，但新增 CSS import 要重啟

Storybook 啟動時 log 出現 `[unplugin-vue-components] component "Index" ... has naming conflicts`，那是 `@nuxt/ui/vite` 的 `ui()` plugin 在跑——證實 builder 確實讀了專案根目錄的 `vite.config.ts` 並合併，`@` 別名與 postcss 也隨之生效。O3 標為未實測的那一點成立。

另一件事是操作上的：在 Storybook 已經跑著的情況下往 `preview.ts` 新增 CSS import，HMR 不會帶進來——瀏覽器端量到的是 `styleSheets` 只有 Storybook 自己的 3 份、`.p-4` 與 `.editor-layout` 都不存在，且 console 出現 `504 (Outdated Optimize Dep)`。重啟 dev server 後才變成 5 份、Tailwind 與 app 樣式都在、`<html>` 背景為 `rgb(9, 9, 11)`。改 preview 的 import 之後要重啟，不能只靠熱更新。

### 3 Storybook 掛在 /dev/storybook/<component> 的方式

- **state:** 否決
- **basis:** → O1

Storybook 以自己的埠與原生 URL 提供（管理介面 `/?path=/story/<title>--<name>`、單一 story `/iframe.html?id=<id>`），**不掛進 app 路由、不設 base path**。`src/router/index.ts` 與 `/dev` 既有頁面都不動。

原本設想的 `/dev/storybook/<component>` 需要在 app 路由裡包一層 iframe 並維護 component 到 story id 的對照，且 Storybook 必須先 build 或並行跑著。相對於「多記一個埠」，這個代價不划算。

story 的入口因此是 `pnpm storybook`，見第 1 格。

### 4 無外部依賴元件的 story

### 6 Vue Flow 元件的 decorator 與 story

- **state:** 待實作
- **needs:** 2
- **basis:** → O4

`FlowChart/` 的 7 個元件靠 inject 取得畫布上下文，需要一個把元件包進 `<VueFlow>` 並餵最小 `nodes` / `edges` 的共用 decorator。decorator 本身是這一格的主要成本，story 反而是其次。

節點元件（`DeviceNode`、`MaterialNode`、`ProductNode`、`WarehouseNode`、`PendingImportNode`）與邊元件（`FlowEdge`）的最小上下文不同，可能需要兩個 decorator。

判準：7 個元件都能掛載且不噴 inject 警告。

### 7 story 的 CI 涵蓋與互動測試

- **state:** 否決
- **basis:** → O1

story 不納入 CI，也不裝 `@storybook/addon-vitest` 與 Playwright。`validate-all` 維持四步不變，`build-storybook` 不進 CI。

理由是專案目前沒有規範 story 品質的規章：沒有定義一個元件該有哪些 story、story 壞掉算不算擋合入、誰負責維護。在這些沒定之前把 story 綁進 CI，只會產生一道沒人知道該怎麼修的紅燈。

要重啟這件事，先立規章再開新格，不在本格續做。
