## 主題簡述

CR-06 藍圖匯入 / 匯出 —— 把目前產線的完整狀態序列化為自包含的 `.html` 記錄檔供分享與離線瀏覽，並支援從 `.html` 或 `.json` 還原，含跨版本 migrate。這是 top spec「社群共享」核心價值的唯一落地點。

規格出處 `spec/06_export_import.md`（v0.3），整份屬 Phase 2，依賴 CR-01 至 CR-05 的狀態。

**本計畫的約束**

- `spec/` 是對外文件，統籌決斷寫在本計畫，不寫回 `spec/`。
- `待實作` 代表「規格已定、尚未逐項對照程式碼確認」；本 CR 在 `src/` 中沒有找到對應實作（見 O1），是本批計畫中少數真正從零開始的。
- 匯入的 JSON 來自使用者提供的檔案，屬外部輸入，必須做 schema 驗證（`CLAUDE.md` 第 9 節），不得直接信任。

## 規劃描述

依 spec 主要章節切格：匯出觸發、人類可讀層四 Tab、記錄檔的輕量互動、機器可讀層、自包含與離線、Zod 版本化與 migrate、匯入流程，最後以驗證表格收斂。

「記錄檔僅供瀏覽」是本 CR 貫穿全部格子的設計原則：視覺從簡、資料求完整。實作時最大的誘惑是把模擬器本體塞進記錄檔以求「功能一致」，那會直接違反自包含與體積要求，所以每一格都以「這是靜態呈現」為前提書寫。

版本化 schema 是唯一有長期維護成本的一格：每次藍圖 JSON 欄位變動都要新增版本與 migrate 規則，這條規矩必須寫進開發守則而非只留在 spec。

## 觀察與推論

### O1 · 2026-08-11 03:25:00+08:00 — 匯出匯入在 src/ 中無對應實作

`src/` 下沒有任何與匯出、匯入、序列化、Zod schema 或 migrate 相關的檔案。`src/types/plan.ts` 與 `src/data/plans.ts` 是專案內的產線資料結構，不是匯出格式。專案依賴中是否已有 Zod 尚未確認。

所以本 CR 是本批 12 份計畫中唯一完全未動工的功能模組。它同時也是唯一需要定義「對外資料格式」的模組 —— 一旦有使用者匯出過檔案，格式就不能隨意改，只能加版本。這使 0009#6（schema 版本化）實質上是本 CR 的第一格，應先於任何匯出實作定案。

### O2 · 2026-08-11 03:30:00+08:00 — 記錄檔內容跨越五個 CR 的呈現結果

spec 2.1 節的四個 Tab 分別對應：產線佈局（CR-01 + CR-02）、流程 Flow Chart（CR-05）、產能估算（CR-04 + CR-10）、警示列舉（CR-03 + CR-09 + CR-10）。四個 Tab 都要求靜態呈現而非重新實作互動。

代表本 CR 沒有自己的資料，它是五個 CR 結果的另一種渲染。所以每個 Tab 的正確性取決於上游 CR 是否已收斂 —— 在 Phase 1 的 CR 全數通過驗證之前做匯出，等於在對移動中的目標序列化。這支持 spec 把整份 CR-06 排在 Phase 2。

### O3 · 2026-08-11 05:00:00+08:00 — 確認完全未動工，且 Zod 尚未進依賴

複查 `src/` 全樹：沒有任何匯出、匯入、序列化、schema 或 migrate 相關檔案，`package.json` 的 dependencies 只有 Nuxt UI、Vue Flow 四件、VueUse、Pinia、Vue、Vue Router —— **沒有 Zod**。`CLAUDE.md` 第 9 節要求外部輸入以 Zod 驗證，所以 0009#6 開工的第一步是加依賴。

另補一項會影響「無損還原」判準的現況：目前沒有任何產線狀態的持久化（`src/` 內唯一的 `useLocalStorage` 在 dev 頁），且 `editorStore` 一啟動就載入寫死的 `mockNodes` / `mockEdges`。所以「匯入覆蓋當前畫布」要覆蓋的東西、以及自動存檔要存的東西，目前都還沒有定義過的初始狀態可言。

### 6 藍圖 JSON 的 Zod schema 版本化與跨版本 migrate

- **state:** 待實作
- **basis:** → O3

以 Zod 定義各版本 schema 並實作 migrate。Zod 尚未在 `package.json` 中，加依賴是本格的第一步（O3）。三條設計原則：migrate 靜默執行，不警示使用者（版本差異屬系統內部處理）；僅在 parse error 時顯示錯誤訊息，告知檔案損毀或格式不合法；每次藍圖 JSON 欄位有變動就新增一個版本並定義對應 migrate 規則。

這一格應先於任何匯出實作定案（O1）—— 格式一旦流出就只能加版本不能改。「每次欄位變動必須加版本」這條規矩要寫進開發守則，否則只會活在 spec 裡。

判準：spec 第 3 節「跨版本 migrate 靜默執行」「多版本鏈式 migrate」兩項通過。

**沿革**

### 7 匯入流程

- **state:** 待實作
- **needs:** 0009#6
- **basis:** → O3

支援 `.html`（內嵌藍圖 JSON 的記錄檔）與 `.json`（直接為藍圖 JSON）。流程：選擇檔案 → 偵測格式並取出原始藍圖 JSON → 版本偵測、跨版本 migrate 與格式驗證 → 驗證失敗顯示錯誤訊息 → 成功後顯示「匯入將覆蓋當前畫布，確定繼續？」確認對話框 → 確認後還原至產線狀態並觸發流量重算與驗證。

輸入來自使用者檔案，屬外部輸入，一律先過 schema 驗證再進 store。

判準：spec 第 3 節「Parse error 顯示錯誤」「匯入覆蓋確認」兩項通過。
