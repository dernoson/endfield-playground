## 1. 決策主體

佈局視角（CR-01 / CR-02 的格子制擺設編輯區）改為自建渲染層，流程視角（CR-05）續用 Vue Flow。五項具體裁決：

| # | 項目 | 裁決 |
| --- | --- | --- |
| 1 | 渲染層 | 佈局視角自建 SVG；流程視角保留 Vue Flow，`@vue-flow/*` 不移除 |
| 2 | 管線歸屬 | 留在 `editorStore`，不另開 `pipelineStore` |
| 3 | 座標型別 | 擴展既有 `Position` 為 `{x, y, z}`，全專案單一座標型別 |
| 4 | 軸向位移 | `AxisMove` 只有 x / y；z 不可移動，是物件屬性而非路徑動作 |
| 5 | 佔用層 | 佔格區間 `z .. z + d - 1`；一般設備 d=2、傳送帶／水管 d=1、部分設備 d=1 |

衍生的模型變化：設備與管線各自持有絕對格子座標、彼此獨立；**連接狀態是每次重算的衍生值，不儲存**。

---

## 2. 為何這樣決策

2.1 Vue Flow 的邊必須兩端都掛在存在的節點上（`createGraphEdges` 找不到節點即丟棄該邊），無法表達「刪除設備後管線留在原地保留斷線」。

2.2 Vue Flow 的邊端點由節點位置導出（`PipelineEdge.vue:18` 讀 `props.sourceX`），節點一動端點必動；需求要的是相反的模型。

2.3 節點旋轉用 CSS `rotate()`，而 Vue Flow 只在節點尺寸變更時重算 handleBounds，transform 不觸發 ResizeObserver —— 旋轉後邊仍連在舊位置，是現況已存在的缺陷。

2.4 連接改為衍生值後，「移動設備後端點對上就自動連接」不再是要實作的功能，而是重算的自然結果。這是本次結構收益的主要來源。

2.5 z 軸不是為了本次變更而發明：`spec/03_validation.md` §2.2.1 早已定義同一套立體碰撞模型，只是編碼不同（見 3.2）。

### 3.2 已對齊，只差編碼

`spec/03_validation.md` §2.2.1 定義的立體碰撞模型與本次裁決逐項相符，換算關係為 `d = h + 1`：

| 物件 | spec `(z, h)` | 佔用層 | 本次 `(z, d)` | 佔用層 |
| --- | --- | --- | --- | --- |
| 一般設備 | (0, 1) | {0, 1} | (0, 2) | {0, 1} |
| 傳送帶 | (0, 0) | {0} | (0, 1) | {0} |
| 水管 | (1, 0) | {1} | (1, 1) | {1} |
| 取貨口／供貨源樁 | (0, 0) | {0} | (0, 1) | {0} |
| 水管系分流器／匯流器／物流橋 | (0, 1) | {0, 1} | (0, 2) | {0, 1} |

無實質衝突，但兩種編碼必須擇一。`h` 只能表達兩種情況、`d` 與 `width`/`height` 單位一致，傾向 `d`；採 `d` 則該節公式與表格一併換算。spec/03 其餘部分（E001/E002/E003 定義、偵測器不負責分類）與現行程式碼一致，不改。

> **✅ 2026-08-25 主編裁決：採 `d`。** `spec/03_validation.md` §2.2.1 的公式與表格須依 `d = h + 1` 一併換算，列入 §3.1 必須修改清單。
